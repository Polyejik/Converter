# Portfolio Pulse — Supabase integration foundation

Статус: миграции и отдельный адаптер подготовлены; живой проект Supabase не подключён. Текущий интерфейс v38 продолжает работать как локальное демо. Не импортировать демонстрационные имена/HR/ставки как реальных сотрудников.

## Запуск

1. Создать отдельный проект Supabase для Portfolio Pulse. Выбрать регион с учётом компании и её требований к данным.
2. Применить три SQL миграции из `migrations` по порядку в SQL Editor или Supabase CLI. Проверить ошибки и не переходить далее при неуспешной миграции.
3. В Auth отключить свободную регистрацию, создать/пригласить первого пользователя через административный интерфейс. Выбрать production redirect URL; локальные URL разрешать только для тестового проекта.
4. В SQL Editor создать компанию, затем membership первого CEO. Использовать UUID реального пользователя из Auth Users. Не брать роль из user_metadata.

```sql
insert into public.pulse_tenants(name) values ('Company') returning id;
-- Replace both UUID placeholders before running.
insert into public.pulse_memberships(tenant_id,user_id,role)
values ('TENANT_UUID','AUTH_USER_UUID','ceo');
insert into public.pulse_profiles(tenant_id,user_id,name)
values ('TENANT_UUID','AUTH_USER_UUID','CEO');
```

5. Подключить адаптер `client.mjs`, передав Project URL и **publishable key** (`sb_publishable_...`). Secret/service_role ключ в интерфейс не помещать. Вход — email/password через Supabase Auth. Адаптер держит сессию в памяти; после перезагрузки требуется вход. UI для входа и полноценная замена текущего хранилища требуют следующего этапа подключения, после получения проекта.
6. Прогнать интеграционные проверки в тестовом облачном проекте: две компании; все шесть ролей; чтение чужого проекта; изменение роли; изменение tenant; собственное согласование; конфликт версий; закрытый проект; изменение ставки после согласования; архивная дебиторка; private Storage.
7. Настроить резервирование и проверить восстановление до импорта рабочих данных. Согласовать retention и доступ администратора.

## Контракт данных

Проекты содержат рабочие поля и schedule, финансовые счета/поступления и приватные HR поля лежат отдельно. UUID пользователя Auth заменяет локальные `analyst-*`/`engineer-*` идентификаторы. При импорте обязательна явная таблица соответствия сотрудник → Auth User. Одним JSON объектом портфель и HR не импортируются.

Проект обновляется PATCH с фильтром `version=eq.N`; сервер увеличивает версию, пустой ответ становится явным конфликтом/отказом доступа. При конфликте UI должен показать свежую версию и предложить повторно применить изменение, а не молча перезаписать.

Табели записываются только RPC `pulse_save_time` и `pulse_transition_time`; прямые INSERT/UPDATE запрещены. Сервер проверяет область доступа, статус, часы по дням, quarter-hour шаг, замораживает ставку при отправке и запрещает согласовывать собственный табель. Rate snapshot исключён из обычного ответа специалисту. Проекты/финансы сохраняются при архивировании. Архив не равен удалению.

Членства и назначения связываются составными внешними ключами с компанией. Членства выдаёт администратор. RLS включён на всех прикладных таблицах; anon не имеет прав. Первоначальная модель разрешает координатору рабочие изменения собственного проекта, дивизиону — своего дивизиона, контрактнику — счета, бухгалтеру — поступления. Перенос между дивизионами и смена координатора не доступны обычным PATCH: для этого пока требуется администратор; отдельная контролируемая операция будет добавлена при подключении UI.

Вложения доступны через приватные buckets; контракты недоступны специалистам. Проектные файлы используют путь `tenant UUID/project UUID/unique filename`. Удаление и перезапись документов пока не предоставлены — для версии документа создаётся новое имя.

## Проверено и не проверено

`node --test supabase/test/client.test.mjs`: публичный ключ, HTTPS, вход, запрет неподдерживаемых полей, version predicate, конфликт, явный отказ сервера, выход, RPC review payload.

SQL миграции ещё не выполнены на PostgreSQL: в окружении нет PostgreSQL/Supabase проекта. Проверки HTTP выполнены с контролируемыми ответами, не с реальной облачной базой. Это подготовленный фундамент интеграции, а не запущенная серверная версия продукта.
